## 1. Why Complexity Matters

A single problem can often be solved in many different ways. For example, finding a name in a list of one million names can be done by checking every name, or by using a much smarter method. Both give the correct answer, but one may finish in a blink and the other may take minutes.

**Complexity analysis** is the method we use to measure how good an algorithm is, so that we can compare algorithms *before* running them.

We measure two things:

| Measure | Question it answers |
|---|---|
| **Time complexity** | How does the running time grow as the input grows? |
| **Space complexity** | How does the memory usage grow as the input grows? |

**Why not just measure seconds with a stopwatch?** Because the result depends on the computer, the programming language, the compiler, and what else is running. A fast algorithm on a slow computer can look worse than a slow algorithm on a fast computer. We need a measure that is independent of the machine.

---

## 2. Input Size and Counting Steps

The idea is simple:

- Let **n** be the size of the input (number of elements in an array, number of nodes in a list, number of digits in a number, and so on).
- Count the **number of basic operations** the algorithm performs as a function of n. A basic operation is a comparison, an assignment, an arithmetic operation, or an array access.
- We study how this count **grows** when n becomes very large.

**Example:** Sum of all elements of an array.

```cpp
int sum = 0;                    // 1 operation
for (int i = 0; i < n; i++) {   // loop runs n times
    sum += a[i];                // 1 operation each time
}
return sum;                     // 1 operation
```

Total operations are roughly `n + 2`. If n = 1,000,000 then the work is about one million steps. The "+ 2" is insignificant compared to n. This observation leads directly to asymptotic notation.

---

## 3. Time Complexity

**Time complexity** is the number of basic operations an algorithm performs, expressed as a function of the input size n.

Consider three functions that count steps of three different algorithms:

| n | Algorithm A: 5n | Algorithm B: n² | Algorithm C: 2ⁿ |
|---|---|---|---|
| 10 | 50 | 100 | 1,024 |
| 100 | 500 | 10,000 | 1.27 × 10³⁰ |
| 1,000 | 5,000 | 1,000,000 | astronomically large |

When n is small, the difference is hard to notice. When n is large, the difference is enormous. Complexity analysis focuses on this **growth rate** for large n.

## 4. Asymptotic Notations

### 4.1 The Problem These Notations Solve

Suppose we count the exact steps of an algorithm and get `f(n) = 3n + 5`. Is this exact formula useful? Not really, because:

- The exact count changes with the computer and the way we count.
- When n is large, the `+ 5` hardly matters, and the `3` is just a constant factor.

What we really care about is the **shape of growth**: does the work grow like n, like n², or like 2ⁿ? **Asymptotic notations** let us describe this shape in a clean way. "Asymptotic" simply means "what happens when n becomes very large."

There are three notations. Think of them as three different kinds of promises about an algorithm.

| Notation | Promise in plain words | Symbol idea |
|---|---|---|
| **Big-O**: O | "It will take **at most** this much work." | Upper bound (ceiling) |
| **Big-Omega**: Ω | "It will take **at least** this much work." | Lower bound (floor) |
| **Big-Theta**: Θ | "It will take **about exactly** this much work." | Tight bound (both) |

### 4.2 Big-O: The Ceiling ("At Most")

**Idea:** Big-O tells us the algorithm will **never be worse than** a certain growth rate.

**Everyday example:** You say, "My journey from Sylhet to Dhaka will take **at most** 8 hours." It might take 5 or 6 hours, but it will not take more than 8. That is a ceiling.

**Formal definition:** We write `f(n) = O(g(n))` if we can find two positive constants **c** and **n₀** such that

```
f(n) <= c * g(n)    for every n >= n0
```

In words: after some starting point n₀, the function f(n) stays below c times g(n).

**Worked example:** Show that `f(n) = 3n + 5` is `O(n)`.

We need to find c and n₀. Try c = 4 (a bit more than 3):

| n | f(n) = 3n + 5 | c·g(n) = 4n | Is f(n) <= 4n? |
|---|---|---|---|
| 1 | 8 | 4 | No |
| 2 | 11 | 8 | No |
| 4 | 17 | 16 | No |
| 5 | 20 | 20 | Yes |
| 10 | 35 | 40 | Yes |
| 100 | 305 | 400 | Yes |

From n = 5 onward, `3n + 5 <= 4n` is always true. So **n₀ = 5** and **c = 4** work, and therefore `3n + 5 = O(n)`.

This also shows why n₀ exists: for very small n the inequality may fail, but we only care about large n.

**Important point:** Big-O is a ceiling, so a higher ceiling is also true. `3n + 5` is `O(n)`, and it is also `O(n²)` and `O(n³)`, because it never exceeds those either. But these are loose and unhelpful. **We always give the smallest (tightest) ceiling we can prove.**

### 4.3 Big-Omega: The Floor ("At Least")

**Idea:** Big-Omega tells us the algorithm will **never be better than** a certain growth rate.

**Everyday example:** "My journey will take **at least** 4 hours." Even with no traffic, you cannot do it faster. That is a floor.

**Formal definition:** We write `f(n) = Ω(g(n))` if we can find positive constants **c** and **n₀** such that

```
f(n) >= c * g(n)    for every n >= n0
```

**Worked example:** Show that `f(n) = 3n + 5` is `Ω(n)`.

Take c = 3. For every n >= 1, `3n + 5 >= 3n` is true (because 5 is positive). So **c = 3** and **n₀ = 1** work, and `3n + 5 = Ω(n)`.

### 4.4 Big-Theta: The Tight Fit ("Exactly")

**Idea:** Big-Theta says the function is squeezed between a floor and a ceiling of the **same growth rate**. This is the most precise statement.

**Everyday example:** "My journey takes **about 6 hours**, give or take a little." The time is bounded closely from both sides.

**Formal definition:** We write `f(n) = Θ(g(n))` if both of these are true:

```
f(n) = O(g(n))    and    f(n) = Ω(g(n))
```

Equivalently, there are constants c₁, c₂ and n₀ such that

```
c1 * g(n)  <=  f(n)  <=  c2 * g(n)    for every n >= n0
```

**Worked example:** For `f(n) = 3n + 5` we already showed `O(n)` (Section 4.2) and `Ω(n)` (Section 4.3). Since both hold, `3n + 5 = Θ(n)`.

### 4.5 A Complete Example with n²

Let `f(n) = 3n² + 2n + 1`. Find its O, Ω and Θ.

**Upper bound.** For every n >= 1 we have `2n <= 2n²` and `1 <= n²`. So

```
3n² + 2n + 1  <=  3n² + 2n² + n²  =  6n²
```

Therefore `f(n) <= 6n²` for n >= 1. This gives `c = 6`, `n₀ = 1`, so **f(n) = O(n²)**.

**Lower bound.** For every n >= 1, `3n² + 2n + 1 >= 3n²`. This gives `c = 3`, `n₀ = 1`, so **f(n) = Ω(n²)**.

**Tight bound.** Both hold, therefore **f(n) = Θ(n²)**.

**Shortcut:** You rarely need to prove this each time. Just keep the biggest term and drop its constant: `3n² + 2n + 1` becomes `n²`. That is exactly what Section 5 teaches.

### 4.6 What Is True and What Is Not

For `f(n) = 3n + 5`:

| Statement | True? | Reason |
|---|---|---|
| f(n) = O(n) | Yes | Tight ceiling |
| f(n) = O(n²) | Yes | Correct but loose ceiling |
| f(n) = O(log n) | **No** | f(n) grows faster than log n, so log n is not a ceiling |
| f(n) = Ω(n) | Yes | Tight floor |
| f(n) = Ω(1) | Yes | Correct but loose floor |
| f(n) = Ω(n²) | **No** | f(n) grows slower than n², so n² is not a floor |
| f(n) = Θ(n) | Yes | Both O(n) and Ω(n) hold |
| f(n) = Θ(n²) | **No** | Ω(n²) fails |

**Rule of thumb:** Θ(g(n)) exists only when the ceiling and the floor have the same growth rate.

### 4.7 Applying Them to a Real Algorithm: Linear Search

| Situation | Steps | Notation |
|---|---|---|
| Key is at the first position (best case) | 1 | Ω(1): the algorithm can never do less than one comparison |
| Key is at the last position or missing (worst case) | n | O(n): the algorithm never needs more than n comparisons |
| Worst case alone | n | Θ(n): in the worst case, exactly proportional to n |

So for linear search we say: running time is **O(n)** overall, **Ω(1)** overall, and **Θ(n)** in the worst case. Because the best and worst cases differ, the overall running time has no single Θ.

### 4.8 Summary and Common Confusions

| Notation | Bound type | Reading |
|---|---|---|
| O(g(n)) | Upper | "At most g(n)" |
| Ω(g(n)) | Lower | "At least g(n)" |
| Θ(g(n)) | Tight | "Exactly g(n) growth" |

- **Big-O does not mean worst case.** Big-O is a type of bound. Worst case is a type of input. You can give a Big-O for the best case too.
- **Big-O is not exact time.** It describes how the work grows, not the number of seconds.
- **Smaller ceiling is better information.** Saying "this is O(n²)" about an O(n) algorithm is true but not useful.
- **In practice,** when someone says "the time complexity is O(something)," they usually mean the Big-O of the worst case.

## 5. Rules for Calculating Complexity

**Rule 1: Drop constant factors.**
`O(5n)` becomes `O(n)`. `O(100)` becomes `O(1)`.

**Rule 2: Drop lower-order terms.**
`O(n² + n + 10)` becomes `O(n²)`. The largest term dominates when n is large.

**Rule 3: Sequential blocks add.**
If one block takes O(n) and the next takes O(n²), the total is `O(n + n²) = O(n²)`.

**Rule 4: Nested blocks multiply.**
A loop of n iterations containing another loop of m iterations gives `O(n * m)`.

**Rule 5: Different inputs use different variables.**
Two loops over two different arrays of sizes a and b give `O(a + b)`, not `O(n)`. Nested, they give `O(a * b)`.

**Rule 6: Logarithms.**
When the problem size is divided by a constant at every step, the number of steps is logarithmic. The base of the logarithm is ignored in Big-O, because changing the base only changes a constant factor.

## 6. Common Complexity Classes

From fastest to slowest:

| Notation | Name | Typical example |
|---|---|---|
| O(1) | Constant | Access `a[i]`, push on stack |
| O(log n) | Logarithmic | Binary search |
| O(√n) | Square root | Checking whether n is prime by trial division |
| O(n) | Linear | Linear search, sum of array |
| O(n log n) | Linearithmic | Merge sort, heap sort |
| O(n²) | Quadratic | Bubble sort, selection sort, insertion sort |
| O(n³) | Cubic | Naive matrix multiplication |
| O(2ⁿ) | Exponential | All subsets, naive Fibonacci |
| O(n!) | Factorial | All permutations |

### Growth Comparison

| n | log n | n | n log n | n² | n³ | 2ⁿ | n! |
|---|---|---|---|---|---|---|---|
| 10 | 3 | 10 | 33 | 100 | 1,000 | 1,024 | 3,628,800 |
| 100 | 7 | 100 | 664 | 10,000 | 1,000,000 | 10³⁰ | 10¹⁵⁷ |
| 1,000 | 10 | 1,000 | 9,966 | 1,000,000 | 10⁹ | 10³⁰¹ | too large |

### Examples of Each Class

**O(1): Constant**
```cpp
int first(int a[]) {
    return a[0];            // one step, regardless of array size
}
```

**O(log n): Logarithmic**
```cpp
int binarySearch(int a[], int n, int key) {
    int low = 0, high = n - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (a[mid] == key) return mid;
        else if (a[mid] < key) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}
```
The search range halves each time: n, n/2, n/4, ..., 1. The number of halvings is log₂ n. For n = 1,000,000, binary search needs only about 20 steps.

**O(n): Linear**
```cpp
int linearSearch(int a[], int n, int key) {
    for (int i = 0; i < n; i++)
        if (a[i] == key) return i;
    return -1;
}
```

**O(n log n): Linearithmic**
Merge sort divides the array in half (log n levels) and does O(n) work to merge at each level. See Section 10.

**O(n²): Quadratic**
```cpp
for (int i = 0; i < n; i++)
    for (int j = 0; j < n; j++)
        cout << i << j;     // executes n * n times
```

**O(2ⁿ): Exponential**
```cpp
int fib(int n) {
    if (n <= 1) return n;
    return fib(n - 1) + fib(n - 2);   // two recursive calls each time
}
```
Each call creates two more calls, so the number of calls roughly doubles with every increase of n.

## 7. Analyzing Loops

| Code pattern | Iterations | Complexity |
|---|---|---|
| `for (i = 0; i < n; i++)` | n | O(n) |
| `for (i = 0; i < n; i += 2)` | n/2 | O(n) |
| `for (i = 1; i < n; i *= 2)` | log₂ n | O(log n) |
| `for (i = n; i > 1; i /= 2)` | log₂ n | O(log n) |
| `for (i = 0; i * i < n; i++)` | √n | O(√n) |
| Two nested loops, each to n | n × n | O(n²) |
| Outer to n, inner `j *= 2` to n | n × log n | O(n log n) |
| Two loops one after another | n + n | O(n) |

### Dependent Nested Loop

```cpp
for (int i = 1; i <= n; i++)
    for (int j = 1; j <= i; j++)
        count++;
```

The inner loop runs 1, 2, 3, ..., n times. Total:

```
1 + 2 + 3 + ... + n = n(n + 1) / 2 = (n² + n) / 2
```

Dropping the constant and the lower-order term gives **O(n²)**.

### Loop with Multiplicative Inner Loop

```cpp
for (int i = 0; i < n; i++)
    for (int j = 1; j < n; j *= 2)
        count++;
```

Outer loop: n times. Inner loop: log n times. Total: **O(n log n)**.

## 8. Best, Worst and Average Case

The running time of many algorithms depends not only on the size of the input but also on the **arrangement** of the input.

Take linear search for a key in an array of n elements:

| Case | Situation | Comparisons | Complexity |
|---|---|---|---|
| **Best case** | Key is the first element | 1 | O(1) |
| **Worst case** | Key is last or absent | n | O(n) |
| **Average case** | Key is equally likely to be anywhere | about n/2 | O(n) |

- **Worst case** gives a guarantee: the algorithm will never be slower than this. It is the most commonly reported.
- **Best case** is rarely useful, because it is too optimistic.
- **Average case** is useful but requires assumptions about the input distribution.

**Important:** Best, worst and average are *cases* of the input. Big-O, Omega and Theta are *notations* for bounds. They are different ideas. We can say, for example, "the worst case of linear search is Θ(n)."

**Example: Quick sort.** Average case O(n log n), worst case O(n²) (when the pivot is always the smallest or largest element).

## 9. Space Complexity

**Space complexity** is the amount of extra memory an algorithm needs as a function of n.

```
Total space = Input space + Auxiliary space
```

- **Input space:** memory taken by the input itself.
- **Auxiliary space:** extra memory used by the algorithm (temporary variables, extra arrays, recursion stack).

Usually, when we say "space complexity," we mean the **auxiliary space**.

### Examples

**O(1) space:**
```cpp
int sum(int a[], int n) {
    int s = 0;                 // only a few variables, independent of n
    for (int i = 0; i < n; i++) s += a[i];
    return s;
}
```

**O(n) space:**
```cpp
int* copyArray(int a[], int n) {
    int* b = new int[n];       // extra array of size n
    for (int i = 0; i < n; i++) b[i] = a[i];
    return b;
}
```

**O(n²) space:** Creating an n × n matrix.

### Recursion and Space

Every recursive call is stored in the **call stack**. If the recursion goes n levels deep, it uses O(n) space even if no array is created.

```cpp
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}
```
Time: O(n). Space: **O(n)**, because n calls wait on the stack at the deepest point.

The iterative version of the same function uses **O(1)** space.

### Space of Common Algorithms

| Algorithm | Auxiliary space |
|---|---|
| Bubble, selection, insertion sort | O(1) |
| Merge sort | O(n) |
| Quick sort (average) | O(log n) stack |
| Heap sort | O(1) |
| Binary search (iterative) | O(1) |
| Binary search (recursive) | O(log n) |
| DFS / BFS on a graph with V vertices | O(V) |

## 10. Analyzing Recursive Algorithms

For a recursive algorithm, we write a **recurrence relation**: an equation that describes the running time T(n) in terms of the running time on smaller inputs.

### 10.1 Examples of Recurrences

| Algorithm | Recurrence | Solution |
|---|---|---|
| Factorial | T(n) = T(n-1) + O(1) | O(n) |
| Binary search | T(n) = T(n/2) + O(1) | O(log n) |
| Merge sort | T(n) = 2T(n/2) + O(n) | O(n log n) |
| Naive Fibonacci | T(n) = T(n-1) + T(n-2) + O(1) | O(2ⁿ) |
| Tower of Hanoi | T(n) = 2T(n-1) + O(1) | O(2ⁿ) |

### 10.2 Method 1: Substitution (Unrolling)

Solve T(n) = T(n-1) + 1 with T(0) = 1.

```
T(n) = T(n-1) + 1
     = T(n-2) + 1 + 1
     = T(n-3) + 1 + 1 + 1
     ...
     = T(0) + n
     = n + 1          ->  O(n)
```

### 10.3 Method 2: Recursion Tree (Merge Sort)

T(n) = 2T(n/2) + n

```
Level 0:   n                       -> total work n
Level 1:   n/2   n/2               -> total work n
Level 2:   n/4 n/4 n/4 n/4         -> total work n
...
Level k:   2^k nodes of size n/2^k -> total work n
```

The tree has **log₂ n levels**, and each level does **n** work. Total = **O(n log n)**.

### 10.4 Method 3: Master Theorem (Simplified)

For recurrences of the form

```
T(n) = a * T(n / b) + O(n^d)       where a >= 1, b > 1, d >= 0
```

| Condition | Result |
|---|---|
| a < bᵈ | T(n) = O(nᵈ) |
| a = bᵈ | T(n) = O(nᵈ log n) |
| a > bᵈ | T(n) = O(n^(log_b a)) |

**Examples:**

- Merge sort: a = 2, b = 2, d = 1. Here a = bᵈ (2 = 2), so T(n) = **O(n log n)**.
- Binary search: a = 1, b = 2, d = 0. Here a = bᵈ (1 = 1), so T(n) = **O(log n)**.
- T(n) = 4T(n/2) + n: a = 4, b = 2, d = 1. Here a > bᵈ (4 > 2), so T(n) = O(n^(log₂ 4)) = **O(n²)**.
- T(n) = T(n/2) + n: a = 1, b = 2, d = 1. Here a < bᵈ (1 < 2), so T(n) = **O(n)**.

**Note:** The Master theorem does not apply to recurrences like T(n) = T(n-1) + T(n-2). Use the recursion tree or unrolling for those.

## 11. Amortized Analysis

Sometimes a single operation is occasionally expensive, but most operations are cheap. **Amortized analysis** gives the **average cost per operation over a sequence of operations**, with no probability involved.

### Example: Dynamic Array (`vector` in C++)

When the array is full, it allocates a new array of **double** the size and copies all elements.

- Most `push_back` operations cost O(1).
- Occasionally one costs O(n) because of copying.

For n insertions, the copies happen at sizes 1, 2, 4, 8, ..., n. Total copy work:

```
1 + 2 + 4 + ... + n  <  2n
```

Total cost for n insertions is less than 3n, so the **amortized cost per insertion is O(1)**.

**Difference from average case:** Amortized analysis is a guarantee over a sequence of operations in the worst case. Average-case analysis depends on a probability assumption about the input.

## 12. Time-Space Trade-off

Often we can make an algorithm faster by using more memory, or save memory by accepting slower speed.

**Example: Fibonacci**

| Approach | Time | Space |
|---|---|---|
| Naive recursion | O(2ⁿ) | O(n) |
| Memoization (store computed results in an array) | O(n) | O(n) |
| Iterative with two variables | O(n) | O(1) |

**Example: Checking duplicates in an array**

| Approach | Time | Space |
|---|---|---|
| Compare every pair | O(n²) | O(1) |
| Sort first, then check neighbors | O(n log n) | O(1) or O(n) |
| Use a hash set | O(n) average | O(n) |

There is no universally best choice. The right choice depends on the constraints of the problem.

## 13. Complexity of Common Data Structures and Algorithms

### Data Structure Operations

| Data Structure | Access | Search | Insert | Delete |
|---|---|---|---|---|
| Array | O(1) | O(n) | O(n) | O(n) |
| Singly linked list | O(n) | O(n) | O(1) at head | O(1) at head (known node) |
| Stack | O(n) | O(n) | O(1) | O(1) |
| Queue | O(n) | O(n) | O(1) | O(1) |
| Hash table | N/A | O(1) avg, O(n) worst | O(1) avg, O(n) worst | O(1) avg, O(n) worst |
| Binary search tree | O(log n) avg, O(n) worst | O(log n) avg, O(n) worst | O(log n) avg, O(n) worst | O(log n) avg, O(n) worst |
| Balanced BST (AVL, Red-Black) | O(log n) | O(log n) | O(log n) | O(log n) |
| Binary heap | N/A | O(n) | O(log n) | O(log n) (extract min/max) |

### Searching and Sorting Algorithms

| Algorithm | Best | Average | Worst | Space | Stable |
|---|---|---|---|---|---|
| Linear search | O(1) | O(n) | O(n) | O(1) | N/A |
| Binary search | O(1) | O(log n) | O(log n) | O(1) | N/A |
| Bubble sort | O(n) | O(n²) | O(n²) | O(1) | Yes |
| Selection sort | O(n²) | O(n²) | O(n²) | O(1) | No |
| Insertion sort | O(n) | O(n²) | O(n²) | O(1) | Yes |
| Merge sort | O(n log n) | O(n log n) | O(n log n) | O(n) | Yes |
| Quick sort | O(n log n) | O(n log n) | O(n²) | O(log n) | No |
| Heap sort | O(n log n) | O(n log n) | O(n log n) | O(1) | No |

Bubble sort is O(n) in the best case only when it uses an early-exit flag. Binary search requires a sorted array.

**Fact:** Any sorting algorithm based on comparisons needs at least Ω(n log n) comparisons in the worst case. So merge sort and heap sort are optimal among comparison-based sorts.

## 14. Choosing an Algorithm from Constraints

A typical computer performs roughly **10⁸ simple operations per second**. If a problem has a time limit of 1 second, use the input size n to decide which complexity is acceptable:

| Input size n | Acceptable complexity |
|---|---|
| n <= 10 | O(n!) |
| n <= 20 | O(2ⁿ) |
| n <= 500 | O(n³) |
| n <= 5,000 | O(n²) |
| n <= 10⁶ | O(n log n) |
| n <= 10⁸ | O(n) |
| n > 10⁸ | O(log n) or O(1) |

If n = 100,000, an O(n²) solution needs 10¹⁰ operations, which is far too slow. An O(n log n) solution needs about 1.7 million operations, which is instant.

## 15. Common Mistakes

1. **Confusing the cases with the notations.** Worst case and Big-O are not the same thing (see Section 8).
2. **Ignoring hidden costs.** A line such as `s = s + str` on a string may itself cost O(n) because of copying.
3. **Assuming one loop means O(n).** Check how the loop variable changes. `i *= 2` gives O(log n).
4. **Forgetting recursion stack space.** A recursive function with depth n uses O(n) memory.
5. **Counting only the input size.** If two inputs are involved (for example, arrays of size a and b), use both variables.
6. **Believing Big-O gives exact time.** Big-O describes growth, not seconds. An O(n) algorithm with a huge constant may be slower than an O(n log n) one for practical input sizes.

## 16. Introduction to P and NP

This is an advanced topic included for awareness.

- **Class P:** Problems that can be **solved** in polynomial time, such as O(n), O(n²), O(n³). Examples: sorting, searching, shortest path.
- **Class NP:** Problems whose solution can be **verified** in polynomial time. Every problem in P is also in NP.
- **NP-complete:** The hardest problems in NP. If any one of them is solved in polynomial time, then all of them can be. Examples: Traveling Salesman (decision version), Subset Sum, Boolean Satisfiability (SAT).

Whether **P = NP** is one of the greatest unsolved problems in computer science. For NP-complete problems no polynomial-time algorithm is currently known, so we use approximation or heuristic methods in practice.

## 18. Summary

- Complexity measures how time and memory **grow** with input size n, not the exact seconds.
- Use **Big-O** for the upper bound, **Omega** for the lower bound, and **Theta** for the tight bound.
- Drop constants and lower-order terms. Add sequential blocks. Multiply nested blocks.
- Growth order: `1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < n!`
- Halving or doubling inside a loop gives **log n**.
- Recursion costs **stack space**. Analyze recursion with recurrences, recursion trees, or the Master theorem.
- **Amortized** analysis gives the true average cost over a sequence of operations.
- Faster algorithms often need more memory (**time-space trade-off**).
- Use the input constraints to decide which complexity is acceptable.
